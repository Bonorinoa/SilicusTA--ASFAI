## 2. Rulings (what is in tonight, what is not)

R1. **Validation drops, never rejects, a bad provenance label.** In `validateObjectives`, an unknown name in `from`
is DROPPED from that objective (the objective survives with the names that are real, or "(several)"). Only names we
sent can ever render after "from material:", so the reserved teacher labels stay unforgeable. A batch is refused only
when NO usable objective is left. Material headers in the prompt carry a short id (`M1`, `M2`, ...) plus the name;
the model answers with ids; the host maps ids back to names. Unknown ids are dropped the same way.

R2. **The AI proposes conditioned on the teacher's objectives.** The objectives prompt gets (a) the teacher's
outcomes from the brief, (b) every objective already on the course that is not dropped, each tagged as the
teacher's own or accepted. Instruction: match their wording style and grain, complement them, never repeat or
reword them, fewer is fine. The teacher's objectives are untrusted text in the prompt like the material.

R3. **Writing your own is first-class and always possible** while objectives are not confirmed: before any
proposal, between rounds, after. Propose-from-sources is allowed whenever objectives are not confirmed AND no
earlier model-written proposal is still undecided (same rule shape as suggestions, `SUGGESTIONS_PENDING`). A
teacher who added objectives first can then ask for proposals from sources. Derive-from-answers keeps its rule
(once per course). If any EXISTING host or gate test must be edited to get there, that is the stop signal: the
engineer reports it in the card instead of editing the assertion (`asfai-silicus-education` skill: "Making an
external dependency OPTIONAL is an additive change").

R4. **Objectives are confirmed by one explicit teacher click** (`backend-asks.md` #13), ADDITIVELY: the gate
gains an option `objectivesConfirm: "explicit"`; default stays `"auto"`, so every existing gate test passes
unedited. The mode is STORED per course at creation (in the `course.created` event's meta), because auto-confirm is
derived on replay: flipping a global flag would change the state of every old course. Explicit confirm needs at least
one decided objective and no proposal still waiting.
*Amended 19 Oct, 18:00, after lane B's first run:* the HOST default stays `"auto"` too. `POST /api/courses` accepts an
optional `objectivesConfirm: "explicit"` (any other value or a missing field means auto); the studio's new-course
wizard sends it. A log without the field replays as auto. Reason: defaulting new courses to explicit forced edits to
16 existing host test files, which is the stop signal that the change was not additive. Auto is today's behaviour
(every proposal still needs a teacher decision), so letting a client pick it weakens nothing.

R5. **Errors speak teacher.** Every refusal the studio can show maps from its CODE to three plain parts: what
happened, whether anything was saved or sent, and the one next action (retry, add a source, enter the passcode,
write your own). The host's own message moves into a "Details" disclosure. The table has one home
(`frontend/src/lib/refusals.ts`) and covers at least the codes in section 3.

R6. **One place for sources, and it shows use.** The new-course flow no longer asks for source names. A source is
added once (file, paste, web page) and shows its state: "Read in this tab · 658 characters", "Fetched when Silicus
reads it", then after a proposal round "Used for N proposals" (derived from the view's proposal sources) or "Skipped:
reason" (from the `skipped` list). Legacy courses with names-only rows keep them, show "Attach the file" on the row,
and match an attached file by name ignoring case and extension.

R7. **Onboarding wizard for a new course** (design owned by creative): first-run welcome, then short steps
(course and learners; sources; your objectives, optional; AI check: status plus passcode, with a real diagnosis),
ending on a summary the teacher confirms. The confirm still leaves as the same intents the brief sends today
(answers, then files, then outline) — no new trust path, and nothing is confirmed with nothing on screen. It lands
on Objectives and, if the teacher chose it and there are sources, starts "propose from sources" on that click.

R8. **Narrower shell and real mobile.** Creative decides the grid. Constraint: the document column is readable
width, the shell does not stretch past a comfortable max on 1440+, and at 390 px the sources and the proposals
tray are reachable without horizontal scroll. Judge only from viewport captures (1440x900 and 390x844).

Not tonight (say so if asked): student access to published versions (STATUS §2 item 1), URL preview at add time
(would need the passcode before the AI step), YouTube online, keeping material text across reloads (#16), editing a
confirmed brief (#14).

## 3. Interfaces the lanes meet at

Host (engineer lanes; both hosts, because `host/handler.mjs` is shared):

- `POST /api/courses/:id/objectives/confirm`, body `{ text }` only (the teacher-turn text). 200 with the view.
  Refusals: 409 `OBJECTIVES_PENDING` (a proposal still waits), 409 `NO_OBJECTIVES` (nothing decided),
  409 `OBJECTIVES_AUTO` (an auto-mode course; the UI never offers the button there).
- View gains `objectivesMode: "auto" | "explicit"`.
- `POST /api/courses/:id/materials/propose` unchanged in shape. *Amended at merge (19 Oct, after lane A):* no new
  code. In an EXPLICIT course a new round is allowed whenever the objectives are not confirmed and nothing is still
  waiting; a waiting round refuses with the existing `ALREADY_PROPOSED` (the existing test already pins that case), and
  a confirmed set refuses `OBJECTIVES_CONFIRMED` (409). Auto courses keep the old one-round rule. `MATERIAL_ROUND_PENDING`
  is pinned at 409 by a lane A test but no route emits it.
- Transport (`frontend/src/gate/transport.ts`): `host.confirmObjectives(courseId, { text })`. The browser host gets
  it for free through the shared handler; parity test in `browserHost.test.ts`.
- Codes the refusal table must cover: `WORKER_NOT_CONFIGURED`, `WORKER_UNREACHABLE`, `WORKER_BAD_OUTPUT`,
  `WORKER_TRUNCATED`, `WORKER_FAILED`, `NO_MATERIALS`, `MATERIAL_ROUND_PENDING`, `ALREADY_PROPOSED`,
  `NO_TEACHER_OUTCOMES`, `OBJECTIVES_CONFIRMED`, `OBJECTIVES_AUTO`, `PROPOSE_FIRST`, `SUGGESTIONS_PENDING`, `NO_USABLE_SUGGESTIONS`, `OBJECTIVES_PENDING`,
  `NO_OBJECTIVES`, `PASSCODE_REQUIRED` (wrong code vs cancelled), `RATE_LIMITED` (if the function sends one),
  `URL_UNREACHABLE`, plus a generic fallback that still names what to try.

Frontend (creative lanes) consumes only the above. Strings shared with smoke scripts: when a lane changes a string a
smoke asserts, it lists the change old -> new in its report.
